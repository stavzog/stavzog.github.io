# Vector Shells

There is a change in how the parametric embroidery app handles geometry data. Before, the source of truth of geometry was the DAG stored in the backend and geometric data was represented as nodes that do math on their input points. Now, the source of truth is vector shells plus the DAG. Vector shells are vector shapes that the user defines before they define a stitch pattern.

The line of thinking is that the shape of an embroidery object is decoupled from its stitch pattern. We can have a circle without defining how it is stitched. Then we can attach a pattern to it and that is when we get the finalized embroidery shape. The pattern, though, is not tied to the shape and can change without affecting it. 

The shape is the vector shell. The source of truth is:

```text
Vector Shell + DAG = Embroidery
```

That is, an embroidery object is a vector shell with a generator dag tied to it.

Since vector shells are now part of the source of truth of the embroidery, they have to be represented in the backend

## Representation in the Backend

A vector shell is essentially a list of control points and a type.

```rust
struct VecShell {
    points: Vec<Handle>, // handle is an id for a ugp
    vecgen: usize, // id of the vector generator that reads the points
    filled: bool,
    //...other config..
}
```

Note: The `vecgen` is a sort of blackbox function that the frontend defines and is only used for rendering. The idea at this point is that the backend cannot see this function. It only views an id so that it can map the specific shell to that function. This may be changed later.

The UGPs are already in the backend, so the raw data is there. The question is how can the backend store the semantic structure of those UGPs, this time as vector shapes and not node inputs for the DAG.

## Tying the VecShell to the DAG

In an embroidery design, we expect that each embroidery shape corresponds to a terminal node (node with no outgoing edges, a sink) in the DAG. This is because, unavoidably, a shape has a final set of output points which needs to be generated by a node that does not feed them anywhere else.

The terminal node invariant means that we can match a vector shell with its corresponding embroidery object by matching it with the correct terminal node.

Thus:

```rust
struct EmbroideryObejct {
    vecshell_id: Handle,
    sink_id: Handle
}
```

The backend already has a Shape object that it uses at the packaging step. The packaging step is a step of the run cycle where a terminal node gets "packaged" into a shape. The shape looks like:

```rust
struct Shape {
    /// The handle of the terminal node that generated this shape.
    pub node_handle: Handle,
    /// The index of the generator operation (useful for the UI to know the type).
    pub operation: usize,
    /// The configuration parameters (e.g., color, spacing).
    pub params: [f32; MAX_NODE_PARAMS],
    /// The final interpolated points for this geometric entity.
    pub points: Vec<(f32, f32)>,
}
```

We can repurpose the Shape object to become the Embroidery object by simply adding a `vecshell_id` to it.

However, currently, shape objects are transient. The backend disposes them at the beginning of the run cycle and it rebuilds the list as it processes the dag. If we attatch the `vecshell_id` to them, it means they now have to be persistent. A specific shape (embroidery object) corresponds to a specific vector shell. We can find a way to support this, but, before we do, there are some other things to consider.

## The Translation Step

The translation step refers to the step in the design process where the user wants to apply a pattern to a vector shell. Until that point, the vector shell is represented in the backend as a lightweight `VecShell` object. When the pattern is applied, the `VecShell` needs to be linked to a node in the DAG and the vector shape logic needs to be translated into dag nodes. The question we need to answer is who will handle the translation step.

Our first thought is to handle the translation in the backend. Doing this means, though, that the backend has to know about the details of the vector shape. This will make the `VecShell` object more complicated and we will have to handle vector shape generators as another type of generators in addition to the ones that are handled in the dag.

The vector shapes are already handled in the frontend for rendering. It would be much simpler if we could use those implementations and not have to copy them into the backend. Thus, we should try to handle the translation step in the frontend.

This means that when the user clicks to add a pattern to a vector shell, the frontend sends instructions to create dag nodes in the backend that would generate the shape with the pattern the user requested.

## The Synchronization Problem

Even though we have found a functional way to incorporate the vector shells into the backend, we still have the issue of introducing another source of truth. The translation step makes it so that the dag produced by the frontend can generate the whole embroidery object without ever needing the vector shells.

The proposed translation step evacuates the VecShell's semantic content into the DAG once, and after that the shell is just a label. We end up with a design where the thing you called a "source of truth" is actually a mutable snapshot that goes stale the moment the DAG diverges from it. This means that, by design, the vector shells stop having a role in the system once a stitch pattern gets applied to them. 

Vector shells only work semantically as a way to decouple the shape from the stitch, but the backend does not really recognize them as a source of truth. It only sort of acknowledges their existence records them. At that stage, the only reason for storing them in the backend is so that we can let the frontend know what vector shell each shape object corresponds too.

**We've recreated a synchronization problem between two representations of the same thing.**

An ideal backend design would uphold the principle that without either a vector shell, or a stitch we cannot have an embroidery pattern. Such a backend would utilize the `VecShell` data during every run cycle to build the embroidery data.

## Solution

The core of the synchronization problem is the vecgen blackbox. The fact that the backend cannot see the vector logic is what makes it have to circumvent it.

The key to solving it is in treating **the VecShell as simply a source node in the DAG: a node with no incoming edges that reads UGPs and produces IPs via its vecgen**.

This means the vecgen is essentially the copy of the frontend's vector function, but it outputs discretized points so that the DAG can utilize it as embroidery data.
